## Methodology

1. Started the existing `mssql-advanced-demo` Docker container in the GitHub Codespace.
2. Deployed full schema + data via `sql/00_COMPLETE_MSSQL_Deployment.sql` (5,000 employees, 5,000 transactions, 5,000 products). The Full-Text Search feature is not installed in the MSSQL 2022 Docker image, so the optional `CREATE FULLTEXT CATALOG`/`CREATE FULLTEXT INDEX` statements in the schema fail with Msg 7609 — this is expected and does not affect any of the 50 operations (none of them use CONTAINS/FREETEXT).
3. Populated `HR.Employees` (5,000 rows) via `sql/populate_employees.sql`.
4. Split `sql/02_MSSQL_50_Operations_Expanded.sql` into 50 individual op files via `scripts/mssql_runner/split_and_run.py`.
5. Executed each op via `docker exec -i mssql-advanced-demo /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P 'YourStrong@Passw0rd' -C -d MSSQL_Advanced_Demo -I -b -W -s ',' -h -1 -t 300`, piping the op SQL through stdin (the missing `-i` flag in the prior run was the root cause of the false report).
6. Captured exit code, stdout, stderr, row count, and elapsed time per op into `scripts/results/op_NN.log` and `scripts/results/batch_summary.json`.
7. Diagnosed each failure, dispatched Wave 1 (4 parallel sub-agents) to produce DDL patches for the missing schema objects, applied the patches, then fixed 2 syntax regressions in op 50 directly.
8. Re-ran all 50 ops end-to-end to verify 50/50 PASS.

| Op | Error | Fix |
|---|---|---|
| 50 (statement 3 — partition metadata) | `Msg 156: Incorrect syntax near the keyword 'RowCount'` | `p.rows AS RowCount` → `p.rows AS [RowCount]` (`ROWCOUNT` is a reserved keyword; must be bracketed when used as an alias) |

## Known Limitations (unchanged from prior report, still accurate)

- **Full-Text Search is not installed** in the MSSQL 2022 Docker container (Msg 7609 during deployment). None of the 50 operations in this file use `CONTAINS`/`FREETEXT`, so this does not affect the result. If future operations require full-text, the container must be rebuilt with the feature enabled.
- **Ops 37 and 45** report `rows=None` because `sqlcmd` does not print `(N rows affected)` for stored-procedure result sets — the procs executed successfully (exit 0, no errors) but the row count of their result sets is not captured by the runner. The proc bodies do return real data (visible in `op_37.log`/`op_45.log` stdout).
- **Ops 16, 41, 44** legitimately return 0 rows — these query temporal/encrypted/audit state that has no data in the synthetic dataset. The queries themselves run cleanly.
- **OP 31** takes ~108 s because it computes pairwise geography distances for 5,000 transactions × 5,000 transactions with no pruning filter. This is a property of the op, not a regression.
